## Verdict

**Revise before acceptance.**

The plan gets the central scientific choices right: it rejects conditional
expectation values as pseudo-mass, uses one both-direction CLOSEST
construction, keeps Top-K out of the estimator, removes the silent precomputed
semantic shortcut, and separates construction, summary, selection, color, and
inspector state.

Four contract/provenance defects remain blocking:

1. the proposed canonical `rank.by = "auto"` rule can select a primary-support
   metric that is entirely unavailable;
2. the proposed `mass.source` result cannot be recovered from the current
   canonical object;
3. the plan retains a default finite-induced-subgraph path whose changed graph
   semantics and identifier complexity are not justified by a current eligible
   source; and
4. `gflow` package version is not a unique source/build identity for either
   handoff provenance or cache validity.

No implementation should begin until these four items are resolved in the
plan. The remaining findings are nonblocking plan improvements.

## Audit Independence And Scope

The auditor did not author the plan, handoff, code, tests, or scientific assets
under review. The implementer handoff was treated as evidence, not as the audit
agenda. Scope followed the Worker-Auditor Audit Charter from the scientific
source contract outward through measurement, selection, provenance, API
correctness, state invalidation, and rendering.

This was a planning phase. It produced no new data, scores, predictions,
statistical comparisons, figures, or reports. Consequently:

- data-generation, held-out measurement, selection fairness, and statistical
  inference checks are not applicable to a new experimental result;
- the relevant scientific checks are the meaning and alignment of the scalar
  field and vertex mass;
- the relevant implementation checks are whether the proposed contracts are
  representable, deterministic, provenance-bearing, and testable.

## Findings

### Artifacts And Provenance

#### A-01 — BLOCKER — Distinct `gflow` source revisions share the proposed cache identity

Evidence:

- The plan names `gflow` as a required dependency but records only the
  `gflowui` baseline at
  `dev/basins_canonical_complex_modification_plan.md:4-6`.
- The handoff likewise records only the `gflowui` branch and commit at
  `dev/basins_canonical_complex_plan_auditor_handoff.md:3-9`, despite basing
  decisions on files in the separate `gflow` repository.
- The cache and migrated-asset contracts use `gflow` package version at
  `dev/basins_canonical_complex_modification_plan.md:175-182` and
  `dev/basins_canonical_complex_modification_plan.md:653-666`.
- The audited `gflow` checkout is commit
  `92a61c086f2fa1fa77223edfb02b74a1be3f1a28`, described by Git as
  `v0.2.0-1-g92a61c08`, while
  `/Users/pgajer/current_projects/gflow/DESCRIPTION:1-3` and
  `packageVersion("gflow")` both report `0.2.0`.

Impact:

A cache generated by the tagged `v0.2.0` code and a cache generated by the
post-tag source checkout can have the same proposed key. The same collision can
occur repeatedly during development when source changes do not bump
`DESCRIPTION`. A stale canonical complex could therefore be accepted as
current even though constructor, adapter, or C++ behavior changed.

Required revision:

- Record the exact `gflow` commit and worktree status in the plan and handoff.
- Define a build/source identity for construction provenance and cache keys,
  such as an installed-build artifact digest, package build ID, or Git commit
  plus a dirty-source/content digest.
- Keep semantic package version as display metadata, not as the sole cache
  invalidator.
- Add a test proving that two different `gflow` builds with the same
  `DESCRIPTION` version cannot share a construction cache entry.

### Estimator And API Correctness

#### A-02 — BLOCKER — `auto` tests mass presence, not ranking-measure availability

Evidence:

- The proposed rule selects `primary.support.mass` whenever `vertex.mass` is
  present at
  `dev/basins_canonical_complex_modification_plan.md:65-75`.
- The proposed explicit-mass rule correctly recognizes that primary mass can
  be "entirely unavailable" at
  `dev/basins_canonical_complex_modification_plan.md:274-280`, but the `auto`
  rule does not apply the same availability check.
- Canonical methods can deliberately have no primary assignment. For RTCB,
  `/Users/pgajer/current_projects/gflow/R/basin_complex_adapters.R:824-865`
  constructs assignments with policy `"none"` while still passing normalized
  vertex mass into the basin table. The invariant is enforced at
  `/Users/pgajer/current_projects/gflow/R/basin_complex_adapters.R:1124-1129`.
- With no assigned primary vertices,
  `/Users/pgajer/current_projects/gflow/R/basin_complex_adapters.R:322-367`
  produces zero `primary.support.size` and `NA`
  `primary.support.mass`.

Independent reproduction:

On the audited nine-vertex graph, both RTCB and overlap-cell canonical objects
returned `status = "ok"`, retained a valid normalized `vertex.mass`, had 18
`not_applicable` assignment rows, and had zero finite
`primary.support.mass` values across five basins. The proposed `auto` rule would
resolve to an all-`NA` ranking vector. Falling back to
`primary.support.size` would not repair those methods because all five values
were zero.

Impact:

The proposed API is a public method on the canonical `basin_complex` class, but
its default is not defined for valid members of that class. The handoff's
limitation that the plan was not checked across methods does not make an
invalid public default safe.

Required revision:

Choose and document one of these contracts:

- constrain the new ranked summary behavior to methods with a usable primary
  assignment, with a specific error or unranked result for other methods; or
- define a method-aware canonical ranking hierarchy that includes a meaningful
  non-primary measure, and test every supported availability pattern.

In either case, resolve `auto` from the finiteness and non-degeneracy of the
candidate measure after retention filtering, not merely from the presence of a
mass vector. Add tests for mass-bearing RTCB and overlap-cell objects, partial
availability, empty retained tables, and direction-specific availability.

#### A-03 — BLOCKER — `summary.basin_complex()` cannot supply the promised semantic `mass.source`

Evidence:

- The plan requires the canonical summary to return mass provenance and a
  `mass.source` field at
  `dev/basins_canonical_complex_modification_plan.md:73-75` and
  `dev/basins_canonical_complex_modification_plan.md:282-295`.
- The UI is expected to distinguish occupation probability, no mass, and a
  named manifest asset at
  `dev/basins_canonical_complex_modification_plan.md:460-471`.
- The current constructor records only the input vector, its normalized value,
  and its total in
  `/Users/pgajer/current_projects/gflow/R/basin_complex.R:1648-1654`. It does
  not retain a semantic source type, asset ID, alignment proof, or source
  fingerprint.

Impact:

`summary.basin_complex(object)` can truthfully report only that explicit vertex
mass is present. It cannot infer whether the vector represents occupation
probability, empirical sampling weights, quadrature weights, or a manifest
asset. Inferring the source from UI labels would violate the plan's own rule.

Required revision:

Assign ownership explicitly:

- either extend the `gflow` constructor/object schema with validated
  `vertex.mass` provenance and make the summary return that stored provenance;
  or
- limit canonical summary metadata to availability and normalization facts,
  while `gflowui` owns and displays the separately validated source/asset
  provenance.

Do not introduce a free-form summary argument that merely relabels an
unverified vector. Add round-trip tests from source contract through
construction, cache, summary, and construction-details display.

#### A-04 — BLOCKER — Default induced-subgraph construction is scientifically unjustified and unsafe

Evidence:

- The plan permits the finite-induced-subgraph adapter and requires only that
  assignments and extrema be mapped back at
  `dev/basins_canonical_complex_modification_plan.md:404-413`.
- The inspector will expose vertex lists in expanded row details at
  `dev/basins_canonical_complex_modification_plan.md:502-517`.
- The current adapter renumbers finite vertices before construction at
  `R/basin_display_helpers.R:30-59`, maps assignment vertices only for the
  categorical display at `R/basin_display_helpers.R:156-170`, and maps the
  compact extremum column at `R/basin_display_helpers.R:172-187`. It returns
  the canonical induced object unchanged at
  `R/basin_display_helpers.R:189-197`.

Independent reproduction:

For the original path `1--2--3--4` with original vertex 2 non-finite, the
finite map is induced `1,2,3 -> original 1,3,4`. The compact table correctly
reported original extremum vertex 3, but the returned canonical table reported
extremum vertex 2, basin ID `basin_max_v00000002`, and support vertices `2,3`
instead of original vertices `3,4`.

Impact:

Automatic vertex removal changes the graph on which the estimator is defined:
it can disconnect components, change improving edges, and create or remove
local extrema and basins. The proposed expanded inspector can also display
wrong graph vertex IDs. Basin and extremum IDs that encode induced vertex
numbers can disagree with their displayed original extrema, undermining
selection, comparison, cache provenance, and migration evidence.

The audited Subject 15 occupation-density source is already complete and
finite. No current source requirement establishes that a partial
conditional-expectation field defines a scientifically intended induced-graph
domain. The added semantics and remapping machinery therefore have no
demonstrated initial-workflow benefit.

Required revision:

- Remove induced-subgraph construction from the default workflow.
- Require every eligible basin source to provide exactly one finite scalar
  value for every graph vertex, with proven vertex alignment.
- Treat any `NA`, `NaN`, or infinite field value as a blocking source error;
  do not compute, retrieve, or display a basin complex for that source.
- Replace the current induced-mapping validation item with tests that confirm
  non-finite fields fail clearly before canonical construction and cannot
  populate or reuse a construction cache.
- Defer induced-subgraph support until a real partial-field use case supplies a
  reviewed scientific specification establishing that excluded vertices are
  outside the estimator's intended domain.

If such a use case is later authorized, it must be designed as an explicit
source-specific mode rather than an automatic cleanup fallback. That future
specification must address changed graph semantics, visible warnings, complete
remapping of every vertex-bearing field and encoded ID, and separate
graph/domain/cache fingerprints.

### Validation And Operability

#### A-05 — MAJOR, NONBLOCKING — The UI validation matrix omits the supported zero-Top-K states

The public summary tests include zero Top-K at
`dev/basins_canonical_complex_modification_plan.md:334-350`, and both sidebar
controls explicitly allow zero at
`dev/basins_canonical_complex_modification_plan.md:419-424`. The `gflowui`
validation matrix at
`dev/basins_canonical_complex_modification_plan.md:762-773` does not explicitly
cover:

- maximum zero with minimum positive;
- minimum zero with maximum positive;
- both zero;
- empty table, empty bulk selection, neutral rendering, and restoration after
  increasing Top-K.

Add those UI/server/renderer tests and an acceptance gate. This does not alter
the scientific estimator, but it closes a directly supported empty-state
contract.

#### A-06 — MAJOR, NONBLOCKING — The reference acceptance has no compute-time or memory budget

The handoff explicitly leaves both-direction cost on 6,529 vertices unmeasured
at
`dev/basins_canonical_complex_plan_auditor_handoff.md:257-260`. The plan leaves
`store.trajectories` and `max.trajectory.length` to implementation judgment at
`dev/basins_canonical_complex_modification_plan.md:99-101`, while the reference
acceptance at
`dev/basins_canonical_complex_modification_plan.md:775-789` requires only that
construction succeed.

Add recorded elapsed time, peak/object memory, cache-hit latency, and the final
trajectory-storage choice to reference-project acceptance. A hard performance
threshold can be deferred until the first benchmark, but the plan should
require a human-facing usability decision based on measured values.

## Reproduced End-To-End Numbers And Falsification Checks

### Both-direction canonical construction

An independent reconstruction of the handoff's nine-vertex graph produced:

```text
status = ok
assignment rows = 18 (9 max, 9 min)
basin rows = 5 (2 max, 3 min)
```

This reproduces the handoff's main constructor claim from source code rather
than from its stated summary.

### Canonical-method counterexample

Using the same graph and a positive mass vector:

```text
method                  status  basins  assignment status  finite primary mass
trajectory_flow         ok      5       18 assigned       5
rtcb                    ok      5       18 not_applicable 0
overlap_cell_complex    ok      5       18 not_applicable 0
```

This falsifies the proposed class-wide equivalence between "mass present" and
"primary mass available."

### CLOSEST threshold/fallback check

On a three-vertex graph with one long improving edge:

- quantile `1` and quantile `0.5` with `allow_and_flag` produced the same
  maximum roots;
- quantile `0.5` recorded fallback attention and use in construction
  provenance;
- quantile `0.5` with `forbid` changed assignments and produced no retained
  basin in the probe;
- quantile `1` made fallback attention false.

This supports the plan's decision to fix the quantile at `1` and keep the
fallback read-only.

### Scientific mass check

The current Subject 15 upstream specification and loader explicitly identify
the field as probability mass, enforce nonnegative finite values, and check
unit column sums. The plan's use of that raw probability vector as both the
CLOSEST field and `vertex.mass` is therefore supported for this source. The
rejection of min-max conditional-expectation pseudo-mass is also scientifically
sound.

The audit did not generalize this conclusion to future occupation-density or
manifest assets; those still require the plan's explicit source and alignment
contract.

## Required Plan Revision Before Re-Audit

The implementer response should map each finding to a concrete plan change,
deferral, or reasoned disagreement. Re-audit should not begin until the revised
plan:

1. makes ranked-summary behavior valid for every canonical method it claims to
   support;
2. assigns and tests semantic mass-provenance ownership;
3. requires complete finite fields in the default workflow and defers
   induced-subgraph construction to a separately reviewed partial-field
   specification;
4. pins `gflow` source/build identity in handoff, provenance, and cache keys;
5. adds zero-Top-K UI tests; and
6. adds recorded reference performance/memory acceptance.

The four BLOCKER findings require correction or explicit human adjudication
before plan acceptance. The two MAJOR findings may be accepted as recorded
implementation requirements if the human investigator chooses not to revise
the plan immediately.
